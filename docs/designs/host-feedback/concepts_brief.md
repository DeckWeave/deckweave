# Shared sound and desktop panels

* **Author:** DeckWeave working hypothesis
* **Date:** 2026-11-03
* **Status:** Six independent BRAINSTORM reviews completed on 2026-11-03. This brief incorporates their findings and root-selected engineering defaults. It is a concept for a bounded design pass, not an approved implementation plan. Proposed APIs and behavior are not implemented, benchmarked or physically accepted.
* **Review anchor:** [Immutable hypothesis](working_hypothesis.md), SHA256 `14B2854797631DF75411411AAE2B32E3E50117C2D09502B812611DB6762023ED`. See the [review report](goldfish_review_report.md) for reviewer status, raw reports, references and dispositions.

## Overview

Plugins need host services for audible feedback and information above other desktop windows. A timer should request a sound and a notification; a note, pinned image or system monitor should use the same panel service without starting another application. Configuration belongs beside the plugin action that owns it.

Profiles remain full sets of pages, folders and actions for one device. They are not part of the panel renderer. Hardware Main/Fn assignments remain common to the device while the active profile resolves host actions.

The owner confirmed that changing profiles must not change or close desktop panels. Profiles are switched frequently like sets of folders and pages. Persistent panels restore after DeckWeave restarts, with their previous content, position and settings. This applies to plugin widgets as well as pinned notes and images; profile changes must not silently turn a working widget into a frozen picture.

## Analysis

### Evidence from the current code

The core already stores a selected profile and additional profiles on each device, each with pages, folders, Fn bindings and an application association. AddProfile, SelectProfile and ProfileApplication are implemented. The editor exposed profile selection and creation behind a small settings icon, with no rename, copy or delete. The accompanying implementation extends that existing model rather than replacing it.

The Audio plugin controls master output through deckweave-platform. That is volume control, not a shared notification sound service. Timers currently render their state and preserve timer handoffs between visible contexts. Their draw path detects completion, but no shared sound or desktop panel API exists. A drawing tick must not become an alarm source: redraw, reconnect or opening a page must not replay an old completion.

The host already has a bounded countdown `TimerPlanner` in `apps/desktop/src-tauri/src/key_lighting.rs`. It arms from accepted timer settings, uses a monotonic deadline and avoids replaying a loaded running state. It is coupled to the bundled countdown, enabled lighting and the current profile. Reuse its deadline/completion logic, while separating durable timer ownership from the physical lighting target and profile. Do not create independent lighting, sound and panel completion authorities. The monitor plugin already shares a two-second CPU/memory sampler; adapt its demand to live service instances for the CPU proof rather than adding another telemetry subsystem.

Plugin processes, property inspectors, host context identifiers and lifecycle handling already exist. Host extensions must be optional and advertised, so ordinary Elgato plugins keep their existing protocol behavior. The plugin SDK and template are sibling repositories under G:/APPS/DW; the contract and example must ship there alongside host support.

The current plugin host retires a visible action slot with `willDisappear` when it leaves the active set (apps/desktop/src-tauri/src/plugins/mod.rs). The SDK then disposes its timers and deletes that context (plugin-sdk/sdk.mjs). Keeping a panel window open while using this retired context would stop updates or retain unusable buttons. Durable panel ownership must therefore be independent of visible device slots. This is an implementation change, not a capability of the current runtime.

### Shared sound service

Proposed calls include `ctx.playSound({ sound, volume, eventId })` and a host-provided list of bundled sounds. Names are provisional. The host validates the live owner, deduplicates event IDs, and bounds request rates, retained delivery records and simultaneous playback. Volume is local to this playback; it must never change master system volume. Use typed asynchronous outcomes or a request handle, not an unqualified success boolean: distinguish unsupported, accepted, duplicate, rejected and cancelled requests, then playback started/finished/failed where observable. Started does not prove that the user heard the sound. Define retry safety and deduplication scope/retention; Preview has its own identity, separate from timer completion.

Start with a small licensed, offline bundle: completion, short notice, and warning. Provide preview and volume in the plugin inspector. Custom local files can follow with a file picker and bounded decoded size; accepting arbitrary URLs or arbitrary paths from plugin messages is unnecessary for the first delivery. Do not launch a player process per sound. The service should sleep when idle, load short samples once as needed, and release audio resources on shutdown or output loss.

Timer integration uses one host-owned run state and deadline, with a stable run identity/revision and explicit start, duration change, pause, reset and cancel. Extract the existing deadline planner into this authority; device rendering, widgets, lighting, sound and completion panels are consumers of its state or event. A drawing tick never creates a completion. Bound active jobs and completion records. Commit adoption before relying on the new authority, and fence legacy writers so an older runtime serializer cannot remove the run marker or become a second authority.

Root-selected defaults preserve existing timer behavior on upgrade: no new sound or panels merely because an update was installed. Adopt common scheduling on a deliberate subsequent start or explicit service opt-in; preserve running/paused/done state and document legacy limitations until adoption. Profile changes and device disconnection do not cancel adopted runs. Close dismisses a timer's panel; Stop/Reset explicitly cancels the run. A fully accepted, persisted host job survives an incidental producer-process crash and may deliver prevalidated native outputs without executing dead plugin callbacks. Explicit plugin disable/removal cancels its jobs.

After DeckWeave restarts, a valid future deadline restores its remaining time; an already elapsed historical timer restores as finished without replaying an old sound. A live run in the same process after Windows sleep may deliver one late completion; select and test clock/resume behavior explicitly. This concept promises neither waking Windows nor alarms while DeckWeave is not running. Physical audio output cannot be an exactly-once transaction with storage: document the crash boundary and prefer suppressing an ambiguous historical attempt to surprising the user with an old alarm. Diagnostics must distinguish that suppression from a successful new delivery.

### Desktop panel service

Separate proposed `open`, `update` and `close` operations, plus events delivered to an authenticated service instance. Names remain provisional. `open` deliberately creates or reopens the identified instance and is idempotent for the same request. `update` changes existing content/live values and never reopens a closed panel. `close` commits closed intent. A visible action can create or configure a panel, but its disappearance does not dispose the panel. Update an existing window in place rather than creating a window for every tick.

The host assigns plugin, service-instance and panel-instance identities. A local name such as `main` is scoped inside its service instance, so two actions from one plugin cannot accidentally replace each other's panel. Never derive durable identity from the visible SDK context. Repeated Show/Open targets the same saved instance without toggling or duplication. Copying an action gives a fresh creation identity but does not automatically open/clone a panel or claim another saved instance. Explicit linking can follow later. These are root-selected implementation defaults, not additional quotations from the owner.

Use structured content first: text/note, image, progress/value, and explicit buttons bound to the owner's registered callbacks. Accept neither arbitrary HTML nor remote script in the first API. The service owns placement, theme, typography, monitor bounds, update coalescing and disposal. This keeps appearance consistent and prevents each plugin from creating its own browser or helper process. The rendering backend is still an engineering decision; a shared service does not by itself prove low memory use. Measure a Tauri implementation against the actual resource requirement before committing to many webviews or a native renderer.

Plugin settings contain monitor, corner/edge/free placement, offset, size, color/opacity, duration or pinned mode, and mouse mode. Separate `interactive` and `click-through`. A click-through panel still needs a recoverable way to move or dismiss it from DeckWeave settings. Showing or updating a panel must not steal keyboard focus. Clamp restored geometry to a connected monitor's work area and handle DPI and monitor removal.

Transient notifications should stack with bounds, expiry and deduplication; an expired transient notification does not reappear after restart. Persistent panels have stable identities, a saved inventory and an explicit close command. Switching a page, folder or profile does not close, reset, duplicate, or re-create them. Closing a persistent panel records that intent so restart does not resurrect it. Device disconnection does not delete desktop content.

Close enters a short pending state and hides the panel only after closed intent commits. If the commit fails, keep it visible with an actionable error and Retry in the panel inventory. Failed content or placement edits retain the last committed state and the unsaved proposal for retry. Preserve closed records or an explicit opening epoch to reject late updates, and separate producer-content authority from user placement/settings authority. Reconnect enumeration and ordinary telemetry cannot reverse close or a completed drag. Button commands are never replayed during reconciliation.

Save content or a managed local image reference, plugin owner, panel instance ID, widget configuration, logical monitor-relative bounds, size, colors, mouse mode and open/closed state. Persist user changes and drag/resize completion, not every CPU sample or animation tick. Restore windows without stealing focus, then reconnect live widgets. Static notes and images render from saved content without starting a plugin solely to redraw them. A missing monitor uses a visible fallback on a connected monitor; retain the preferred placement so temporary monitor removal does not destroy it.

Use a separately versioned host-service database, leaving the existing profile/configuration format untouched. Older builds leave it alone; returning to a new build restores compatible records without replaying old completions. This preserves data on rollback without claiming that an old build can display new panels. Reuse existing transaction/revision and migration conventions; do not add a generic storage framework. Design the inventory/managed-asset commit boundary, host-envelope versions, opaque plugin payload versions and partial recovery explicitly. Preserve unsupported or malformed records as unavailable inventory entries, without blocking valid panels or silently resetting all saved state.

Bound retained records and text/configuration bytes separately from open windows. Bound decoded image dimensions and total managed-asset storage, not only each image. Define replacement, shared references, interrupted writes, orphan cleanup and the distinction between close and explicit removal. Managed copies best match restart restoration; store references rather than embedding large image payloads into every save. Report missing assets and preserve recoverable metadata. Screenshot acquisition remains a separate later command.

The host owns a background service registry for panels and active timer jobs, separate from device visibility. Extend the existing single package supervisor: visible slots and active live services contribute separate bounded demand reasons; static notes/images contribute none. Establish restored service demand before waiting for a hidden-source plugin to register. Do not start a second process for the same package or keep every hidden action alive. Disable/removal, upgrade pause and shutdown override demand.

The plugin registers a versioned widget kind and receives compatible saved instances on reconnect. Authenticate package ownership and use a fresh service connection generation and expected panel revision for updates/clicks. Never persist an opaque WebSocket context, callback closure or old token. Profile changes alone do not retire service registration. Do not repurpose the retired visible-context grace period: it exists for late settings persistence, not background execution.

Clicking a widget targets its saved owner and configuration, never a synthetic press on the same key in the current profile. After creation, the panel owns its saved configuration; the action is a provenance link and inspector entry point. Editing defaults for future panels never silently changes an existing panel. Clearly select the existing instance when editing it, and reuse the same plugin inspector with an explicit panel-settings scope. Generic host placement, locate/reset and close controls remain available from the global Panels inventory, including when the source action is hidden, removed or offline. A missing actionable reference produces an unavailable state instead of executing a different action.

Plugin disable/removal or a crash retires its live callbacks without erasing saved panels. Keep pinned text and images visible. Mark plugin-produced live data unavailable or stale and disable plugin callbacks until the owner reconnects; do not show a cached CPU reading as current. A fully accepted host-owned timer may continue displaying its authoritative run state and deliver native outputs after a producer crash; explicit disable/removal cancels the owner's jobs. The panel inventory always allows close or removal. Plugin reinstallation may reclaim only its own compatible saved widget instances after registration; unsupported versions retain saved content without executing old callbacks. Old Elgato plugins receive no invented visibility or service events: this is an advertised DeckWeave extension.

Version capabilities separately for sound, panels and timer jobs. A new host keeps old plugins' visibility semantics; a new plugin on an old host keeps ordinary controls usable, reports unsupported services and never claims a working background alarm. Include the sibling SDK/types/protocol, template and actual bundled `lib/sdk.mjs` copies in release validation. Updating only the SDK repository does not update installed consumers.

Screenshot capture and image pinning are distinct from displaying an existing image. A later capture command needs a visible area-selection flow, local storage ownership and clear deletion behavior; no background capture. First prove the panel service with a note, timer completion and a CPU value, then add the user-facing screenshot command to that service.

### Resource and failure limits

Use one service per application, bounded panel counts and image sizes, and merge repeated updates to the same panel. Enforce per-owner and global ingress byte/rate/queue/decode limits before expensive work. Replace pending continuous values through a latest-value mailbox; keep close, lifecycle, configuration, timer controls and button presses in bounded ordered acknowledged command paths. SDK throttling is helpful but cannot replace host enforcement. Slow renderer/audio/storage work must not block device input or hold the Core mutex while waiting for windows.

No continuous animation or full-screen redraw for static notes. An idle note causes no plugin polling merely to remain visible. An empty scheduler can wait for a command or deadline; the current lighting worker's cadence is not the new service's idle target. Expose a bounded local diagnostic buffer and service status from the inventory. Correlate package/service/panel/run/request IDs, generation and revision with stable reason codes for registration, quota, stale rejection, save/restore, callback, renderer and playback outcomes. Distinguish deliberate deduplication and historical suppression from failure; measure schedule lateness separately from audio-start latency. Do not log note text, image bytes, tokens or payload dumps.

Engineering owns provisional resource limits and acceptance thresholds. Before renderer commitment, measure the application and child processes against the same baseline using one/four/eight static panels, a live CPU widget, timer output, several distinct owners, a transient burst, oversized images, a noisy owner and close/reopen cycles. Report incremental private memory, idle/loaded CPU, wakeups, update/queue age, restore time, audio/input latency and reclaimed resources. These workloads are not performance claims or supported caps yet. Prefer one Tauri candidate; a second renderer requires a measured reason and an explicit maintenance trade-off.

Sound output loss and panel rendering failures must not stop timers or device input. A plugin process crash marks producer-dependent data unavailable and cancels outstanding plugin callbacks, retaining saved content and accepted host jobs. Multi-monitor placement, click-through, native focus behavior and actual audio quality need real Windows acceptance. Tests of serialization alone cannot establish those outcomes.

## Goals vs. Non-Goals

* **In scope:** shared host sound and panel API, documented SDK support, bundled sound preview, optional timer notification settings, persistent and transient panel primitives, lifecycle and resource bounds, Windows 11 first with platform boundaries for macOS/Linux.
* **Separate existing work:** repair saved IO84 input routing and complete profile management without changing onboard assignments.
* **Not initial scope:** arbitrary plugin web pages inside overlays, a second widget marketplace, streaming video, network image loading, global keyboard capture, or a separate overlay runtime for every plugin.

## Alternatives Weighed

* A player/notification process in each plugin duplicates work and makes performance and cleanup inconsistent. Use a shared host boundary.
* OS notifications alone do not support persistent images and action widgets. They can remain an optional platform delivery method for ordinary notices.
* One full-screen transparent webview makes per-panel hit testing and click-through difficult. One webview per panel may multiply memory. Neither is selected without measurement.
* Closing panels on profile changes conflicts with the owner's confirmed workflow. Keeping only their last screenshot would also break live widgets. Preserve independent panel instances and give them a background service lifetime, with explicit close and unavailable states.
* Replaying saved device-key input for widget clicks can execute a different profile's action. Route by the saved panel owner and fresh service registration instead.
* F13 alone is not proof that a saved keyboard source is ready. Preserve device-specific pairing/readback; do not solve reconnect by falling back to a global hotkey.
* Separate completion schedulers for lighting, sound and panels would multiply pause/reset/replay policy. Extract one timer authority with output adapters. Keeping a generic plugin callback alive for each deadline costs more than a narrowly typed host job and complicates crash recovery.
* Saving panels inside the source action's settings would restore profile coupling. A separately versioned service database isolates older writers; it adds recovery/asset work that must be tested. Preserve existing storage conventions without creating a generic persistence service.
* A single `upsert` hides reopening intent and can defeat durable close. Separate open/update/close and keep producer samples independent of host presentation state. Toggle/share behavior can be a later explicit command.

## Review conclusions and decision ownership

All six fresh-context reviewers completed against the same frozen hypothesis. Four global agent slots required three waves of two; later reviewers received no earlier findings. They identified no concept-invalidating Blocker. The [report](goldfish_review_report.md) consolidates raw findings into 11 Major and 3 Nit items: timer authority/adoption, process admission, instance/edit ownership, durable close, resource budgets, ingress fairness, storage/rollback, assets, capability rollout, typed outcomes/diagnostics and explicit user-visible defaults.

The root's [independent source follow-up](source_followup.md) and [engineering dispositions](implementation_decisions.md) were consulted only after all six reports arrived. They are separate evidence and proposed resolutions, not Goldfish findings or acceptance results. Root selected the repeat/copy, editing, close-versus-stop, crash-continuation and legacy opt-in defaults described above. Those defaults are reviewable design directions; only the persistence/profile constraints are attributed to the owner's explicit confirmation. No further owner answer is required for the next bounded design pass. Database layout, limits, queues, result types and renderer thresholds are engineering decisions to make concrete there.

Remaining engineering work includes exact durable transaction/crash semantics, bounded deduplication retention, run adoption fencing, service schema/capability versions, asset recovery, resource thresholds and physical Windows proof. Do not call the concept implementation-ready merely because these mitigations are written down.

## Confirmed product behavior and acceptance boundaries

On 2026-11-03 the owner confirmed: restart restores the previous state; changing profiles has no effect on the desktop panels. Profiles are independent sets of pages that the user will switch frequently, as in Elgato.

The implementation must demonstrate a persistent note and a live CPU or timer widget while switching pages, folders and profiles; neither may disappear, duplicate or stop merely because its creating action is no longer visible. After a normal application restart, the content, position and settings return without focus theft or repeating an old sound. Closing a panel stays closed after restart. Plugin loss produces an unavailable live widget, and reconnection cannot replay a queued button event. A missing monitor keeps the panel reachable. Automated tests cover ownership and saved state; physical Windows checks cover focus, mouse pass-through, DPI/monitor placement and audible output.
