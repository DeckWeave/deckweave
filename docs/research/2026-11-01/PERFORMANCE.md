# Производительность и выбор интерфейса

Дата: 2026-11-01. Это исследование, а не benchmark нового приложения. После обсуждения владелец принял Rust + Tauri 2 + Svelte; актуальные решения — в [DECISIONS](../../DECISIONS.md). Сравнение вариантов ниже сохранено как основание выбора.

## Нужен ли WebView

При сохранении исходных форм настроек плагинов Elgato нужен браузерный движок: их Property Inspector состоит из HTML/JavaScript. Замена на нативную форму требует отдельной реализации для каждого плагина и перестаёт быть универсальным запуском исходного пакета. [Elgato PI](https://docs.elgato.com/streamdeck/sdk/guides/ui/).

У On Air Clock 1.3.0 `CodePath=index.html`: HTML здесь исполняет и рабочую часть, которая рисует часы. Этот backend нужен при активных назначениях независимо от открытой формы настроек. У VS Code исполняемый файл нативный, но формы настроек HTML. Node-плагину нужен Node.js, что также следует считать отдельно от UI.

Tauri на Windows использует WebView2; меньший размер поставки не доказывает малое потребление RAM. WebView2 включает browser/renderer/helper-процессы. Разные user data folders создают разные группы процессов. [Tauri](https://v2.tauri.app/reference/webview-versions/), [Microsoft process model](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-model).

## Выполненные измерения

ОС Windows 11 Pro 10.0.26200; Intel i9-12900K, 24 логических процессора, около 64 ГиБ RAM. Аппаратные данные: [hardware.json](evidence/hardware.json).

Использованы существующие binaries старого проекта: debug protocol host и release desktop в режиме `--legacy-web`. Хеши — [probe-environment.json](evidence/probe-environment.json). Это не измерение нового приложения, не GPUI/Tauri A/B benchmark и не полный замер редактора.

Каждая одиночная проба: запуск нового временного браузерного профиля, 5 секунд наблюдения, виртуальная кнопка, без keyDown/keyUp. Снимки процессов примерно раз в 300 мс; среднее вычислено по снимкам после второй секунды. В дерево входят protocol host, browser host, WebView2 и его helpers. В работающем Stream Deck другие процессы в эти суммы не включались.

| Проба | Средний private commit, МиБ | Сумма working sets, МиБ | Максимум процессов | Результат |
|---|---:|---:|---:|---|
| Контрольная HTML-страница, запуск 1 | 136.47 | 314.53 | 9 | 3 сообщения setTitle |
| Контрольная HTML-страница, запуск 2 | 157.99 | 362.52 | 9 | 3 сообщения setTitle |
| On Air Clock, запуск 1 | 180.22 | 382.01 | 9 | 21 сообщение setImage |
| On Air Clock, запуск 2 | 180.20 | 380.18 | 9 | 21 сообщение setImage |

Данные: `perf-control-1/2.json`, `perf-clock-1/2.json` в [evidence](evidence/). Working sets включают общие страницы и при суммировании могут учитывать их повторно. Private commit — частная выделенная виртуальная память, не физическая резидентная RAM. GPU/VRAM и полный системный эффект отдельно не измерялись.

Начальный накопитель CPU в этих четырёх файлах вернул недостоверные нули; они помечены `CpuMeasurementValid=false` и не используются. Проверка raw Win32-счётчиков сохранена отдельно в [cpu-counter-validation.json](evidence/cpu-counter-validation.json).

Повторные измерения по разности `KernelModeTime + UserModeTime` дали 0.078125 CPU-секунды за 2.275 с у контрольной страницы и те же 0.078125 за 2.218 с у часов: примерно 3.43% и 3.52% одного логического процессора. Эти короткие интервалы не устанавливают существенную разницу и не доказывают нулевой idle CPU. Делить показатель на 24 и выдавать его за устойчивую системную нагрузку преждевременно. Данные: [контроль](evidence/cpu-control.json), [часы](evidence/cpu-clock.json).

## Два HTML-backend и общее окружение

Два protocol host одновременно запускали копию одного HTML-плагина, каждый со своей виртуальной кнопкой. Снимки — примерно на второй и четвёртой секунде.

Это намеренно два отдельных backend-процесса, а не две кнопки одного плагина в правильном общем host. Один пакет может обслуживать много contexts на разных устройствах. Из этих чисел нельзя выводить линейную стоимость каждой кнопки или виджета.

| Условия | Private commit, МиБ | Сумма working sets, МиБ | Browser roots | Всего процессов |
|---|---:|---:|---:|---:|
| Разные UDF | 350.80 → 364.16 | 747.37 → 772.68 | 2 | 18 |
| Общий временный UDF | 221.01 → 230.73 | 492.45 → 508.21 | 1 | 13 |

Для диагностического shared-варианта переменная `WEBVIEW2_USER_DATA_FOLDER` задана только в окружении дочерних тестовых процессов. Пользовательские/системные переменные не менялись. [Microsoft об overrides](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/webview2-idl).

**Shared-вариант не прошёл проверку завершения:** один host завершился успешно, другой — `ConnectionReset`/10054. В старом host `Drop` уничтожает всё дерево плагина через Windows Job Object. Гипотеза, поддержанная кодом: остановка одного владельца уничтожает общие browser-процессы. Событие сбоя установлено; точная последовательность завершения не трассировалась. Данные: [isolated](evidence/two-clocks-isolated.json), [shared](evidence/two-clocks-shared-udf.json).

Вывод: совместное использование browser runtime действительно может уменьшить накладные расходы, но требует общего владельца жизненного цикла. Один общий путь к данным не является готовым решением. Нельзя переносить одновременно независимый per-plugin kill-tree и разделяемый browser process.

Microsoft предоставляет multi-profile API для разделения browser data внутри одного UDF. Наличие API не доказывает, что нужная изоляция уже доступна через выбранный wrapper: требуется отдельный prototype с проверкой origins, cookies/storage и отказов. Tauri 2.12.5 на Windows документирует `with_environment`; индивидуальный profile API этим исследованием в Tauri builder не установлен. [Microsoft profiles](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/multi-profile-support), [Tauri Windows builder](https://docs.rs/tauri/latest/x86_64-pc-windows-msvc/tauri/webview/struct.WebviewWindowBuilder.html#method.with_environment).

## Сравнение вариантов

| Вариант | Что даёт | Основной риск для этой задачи |
|---|---|---|
| Rust + Tauri 2 + Svelte | Естественная среда HTML-форм, доступные несколько окон, знакомый путь OpenDeck | Постоянный браузерный UI; требуется контролировать количество runtime, IPC и перерисовки |
| Rust + GPUI + browser host | Нативный редактор, возможность не держать браузер для собственных форм | HTML-плагины всё равно требуют движка; добавляются две UI-технологии и их интеграция |
| GPUI с переписанными формами всех плагинов | Браузер можно убрать из поддерживаемого поднабора | Теряется универсальная работа исходных HTML-форм и HTML-backend; постоянное сопровождение адаптеров |

GPUI поддерживает Windows и окна, но upstream предупреждает о pre-1.0/breaking changes. Документация GPUI Kit описывает экспериментальный WebView2: ограничения наложения меню/диалогов, clipping и особую настройку renderer в примере. Это конкретный риск редактора с библиотекой, inspector, drag-and-drop и всплывающими меню. Собственный GPUI-прототип не собран; превосходство по ресурсам не измерено. [GPUI](https://raw.githubusercontent.com/zed-industries/zed/main/crates/gpui/README.md), [GPUI Kit WebView](https://gpui-kit.com/docs/webview/).

## Рекомендация для обсуждения

Выбран Rust + Tauri 2 + Svelte, без переносимого старого редактора и его пользовательского apply-процесса. Причина — сокращение интеграционных рисков при обязательной HTML-совместимости. Выбор не основан на обещании самого низкого расхода RAM. GPUI с отдельным compatibility host был рассмотрен как альтернатива; возвращаться к этому выбору без новых измеренных оснований не требуется.

Предлагаемые инженерные ограничения: окна устройств создаются по запросу; inspector существует для выбранного назначения; backend запускается на пакет, не на кнопку; native действия не требуют browser backend; статические изображения не обновляются таймером; закрытие окна освобождает UI, сохраняя активные действия. HTML-backend нельзя приостанавливать, если на нём работают часы или feedback. Изоляция стороннего кода не должна исчезать ради экономии памяти.

При реализации выбранного стека нужен маленький новый стенд: реестр, два окна, одна HTML-форма, два HTML-backend с общим владельцем; создание/закрытие в разном порядке, повторное открытие и 30–60 минут работы. Замерять весь process tree в release, idle с закрытыми окнами, открытый редактор, перерисовки, input latency и рост памяти. Владелец не может задать численные бюджеты; их следует предложить по результатам типовых измерений, не блокируя работу повторным вопросом — [Q-01/Q-02](QUESTIONS.md).
